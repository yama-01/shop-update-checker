# 開発ドキュメント（背景・仕組み・運用手順）

このファイルは、`README.md`（セットアップ手順）を補足するドキュメントです。
「なぜこう作ったか」「日々の運用（お店の追加・トラブル対応）をどうやるか」
「過去にどんな問題が起きて、どう直したか」をまとめています。今後この
プロジェクトに関わる人が、同じ問題を再度踏まないための記録です。

## 1. このプロジェクトの背景・目的

複数の店舗（風俗業界の求人・在籍案内サイト）を毎日自動で巡回し、
「新しく入店した人（新着）」を検知してLINEで通知するためのBotです。
併せて、その履歴をカレンダー形式で振り返れる集計サイト（`docs/index.html`）も
用意しています。

もともと別プロジェクト（`newface`リポジトリ）が存在していましたが、本プロジェクトは
それとは**完全に独立**した新規リポジトリ・新規Supabaseプロジェクトとして作られています。
既存プロジェクトに影響を与えず、まっさらな状態で構成を見直すためです。

構成方針として、サーバーを自前で立てず「GitHub Actions（定期実行）+ Python + Supabase」
だけで完結させています。サーバー代がかからず、コード（Pythonスクリプト）とデータ
（Supabase）が分離しているため、運用中でも安全にコードを直せます。

## 2. 全体の仕組み

```
[GitHub Actions: 毎日0時JST]        [GitHub Actions: 毎日9時JST]
    crawl.py  ──────────┐                notify.py
    各お店のページを巡回     │            直前0時分のupdate_logsを
    前回との差分を検知       │            系列店ごとにまとめて
    Supabaseに記録          │            LINEに1通で通知
         │                 │                  │
         ▼                 │                  │
    stores.seen_links   update_logs ◀─────────┘
    （既知リンクの記録）    （毎回のチェック結果）
         │
         ▼
   docs/index.html（カレンダーサイト）
   ブラウザから直接Supabaseを読み、
   update_logsを日付ごとに集計して表示
```

- **crawl.py**（毎日0時JST）: 各お店のページを見に行き、前回チェック時から増えた
  リンクを「新着」として検知する。結果は`update_logs`に記録するだけで、LINEには
  何も送らない。
- **notify.py**（毎日9時JST）: 直前0時のcrawl.py実行分（`update_logs`）を読み出し、
  系列店（`group_name`）ごとに合算して、1通のLINEダイジェストとして送信する。
- なぜ2本に分けているか: 巡回とLINE送信を分離することで、「今日は何時に何件通知が
  来るか」が安定し、また巡回だけを手動で試したいとき（新しいお店を登録した直後の
  動作確認など）にLINEを誤送信せずに済む。

### なぜ「9時に前日分をまとめて通知」なのか

0時に実行したcrawl.pyが検知した新着は、「昨日1日の間に増えた新着」という意味に
なります（0時のチェック = 前日24時時点のスナップショットとの比較）。そのため、
notify.pyは「日付を1日ずらして」報告する作りになっています。詳しくは
「6-2. 活動日(activity_date)のズレに注意」を参照してください。

## 3. データモデル

### `stores`テーブル

| カラム | 内容 |
|---|---|
| `id` | 主キー |
| `name` | LINE通知に表示するお店の名前 |
| `url` | 巡回するページのURL |
| `type` | 監視方法。`page` / `rss` / `cast_list` / `girl_list` / `profile_list` / `custom_pattern`（詳細はREADME参照） |
| `link_pattern` | `type=custom_pattern`の場合に使う、新着リンクを判定するための正規表現 |
| `link_container_selector` | `type=custom_pattern`の場合に任意で使う、ページ内の特定エリアだけに絞り込むCSSセレクタ（例: `ul.girls-list`）。中央カラムと右カラムに同じ形式のリンクが混在するサイト向け |
| `is_staff_list` | 通知文言を「〇名の入店がありました」にするかどうか |
| `group_name` | 系列店・グループ名。同じ名前の店舗はLINE通知・カレンダーで合算表示される |
| `seen_links` | これまでに検知済みのリンクの識別キー一覧（jsonb配列）。次回チェック時にこれと比較して新着を判定する |
| `enabled` | `false`にするとそのお店は巡回対象から外れる |
| `last_checked_at` | 最終チェック日時 |
| `created_at` | 登録日時 |

### `update_logs`テーブル

毎回のチェック結果を1店舗・1回のチェックにつき1行記録する。過去分は削除せず
すべて保持する方針（カレンダーサイトで全期間さかのぼれるようにするため）。

| カラム | 内容 |
|---|---|
| `id` | 主キー |
| `store_id` / `store_name` / `group_name` / `store_type` / `is_staff_list` | チェック時点の店舗情報のスナップショット |
| `checked_at` | チェックした日時（UTC） |
| `status` | `first_check`（初回） / `updated`（新着あり） / `no_update`（新着なし） / `error`（取得失敗） |
| `new_count` | 検知した新着の正確な件数 |
| `new_items` | 新着の詳細（`{"title":..., "url":...}`の配列）。**最大10件まで**しか保存されない（`crawl.py`の`SAMPLE_ITEMS_LIMIT`）。LINE通知にはさらにそのうち先頭3件だけが表示され、残りは「…ほか◯件」とまとめられる。件数(`new_count`)自体は10件を超えても正確 |
| `error_message` | `status=error`の場合のエラー内容 |

カレンダーサイト（`docs/index.html`）は`status=updated`の行だけを取得し、
「活動日」ごとに`new_count`を合算して表示している（`no_update`/`first_check`/`error`は
集計対象外）。

## 4. 新しいお店を追加する手順（運用マニュアル）

1. お店の一覧ページのURLと、その中にある「実際に新人プロフィールへ飛ぶリンク」の
   実例を1つ用意する。
2. **ブラウザで見えるリンク（クリック後に遷移した先のURL）を鵜呑みにしない。**
   `crawl.py`はページのHTMLソースに書かれている`<a href>`をそのまま見るだけで、
   リダイレクト（自動転送）を一切追いかけない。ブラウザは転送後のURLを表示する
   ことがあるため、実際に登録すべきパターンとズレることがある（6-1節参照）。
   実際のソースを確認するには、ブラウザで対象ページを開いて
   `view-source:` を先頭につけたURL（例: `view-source:https://example.com/list`）を
   開き、目当てのリンクをそのHTML上で確認する。
3. リンクの中の「人物ごとに変わる部分」（数字のIDなど）を見つけ、それを`\d+`に
   置き換えた正規表現を`link_pattern`として組み立てる。
   - IDがパスに含まれる例: `/girls/detail/85574` → `/girls/detail/\d+`
   - IDがクエリ文字列に含まれる例: `girl.php?id=12345` → `girl\.php\?id=\d+`
     （`?`はそのままだと「直前の文字が0か1個」という正規表現の記号になってしまうため、
     文字として使いたい場合は`\?`のようにエスケープ（バックスラッシュを付ける）する
     必要がある）
4. 同じ形式のリンクがページ内の別の場所（サイドバーのランキング等）にも出てきて
   誤検知しそうな場合は、`link_container_selector`でエリアを絞り込む
   （5節参照）。
5. Supabaseの`stores`テーブルに、`name` / `url` / `type=custom_pattern` /
   `link_pattern` / （必要なら`link_container_selector`）/ `group_name`などを入力して
   1行追加する。`seen_links`は空欄のままでよい（初回チェックで自動的に現在の
   一覧が基準として保存される）。
6. GitHub Actionsの「Crawl stores」を手動実行（`workflow_dispatch`）し、ログで
   そのお店が`[初回]`と表示され、エラー・警告が出ていないか確認する。

## 5. `link_container_selector`の使いどころ

サイトによっては、本来拾いたい一覧（例: 中央カラムの新人一覧）と同じ形式の
リンクが、ページ内の別の場所（右カラムのランキングやフォトダイアリー等）にも
出てくることがある。この場合`link_pattern`だけでは区別できない。

対応するには、実際のページのHTMLソースを見て、拾いたいエリアを囲っている
タグ（`<ul class="...">`や`<div id="...">`など）を特定し、そのCSSセレクタを
`link_container_selector`に設定する。設定すると、`crawl.py`はページ全体では
なく、そのセレクタに一致する最初の要素の中だけを見るようになる（`fetch_pattern_list_links`
関数を参照）。未設定なら今まで通りページ全体が対象になる。

例: `https://e1ns.jp/girls/newcomer-list` は、中央カラムの新人一覧が
`<ul class="girls-list">`というタグで囲まれている一方、右カラムのランキング等は
`<div class="aside-live">` `<div class="aside-photo">`という別のタグで囲まれていた。
`link_container_selector`に`ul.girls-list`を指定することで、右カラム分を
除外できた。

このセレクタの特定には、ブラウザの「ページのソースを表示」
（`view-source:URL`、または`Ctrl+U` / `Cmd+Option+U`）で該当箇所のHTMLを
確認する必要がある。分からない場合は、ページソースを`.html`ファイルとして
保存して共有してもらえれば、開発側で特定できる。

## 6. 過去に起きた問題と教訓

### 6-1. リダイレクトの罠

`crawl.py`は`requests.get()` + BeautifulSoupでページのHTMLを取得するだけで、
リンクをクリックした後の自動転送（リダイレクト）は一切追いかけない。そのため、
ブラウザで「実際にクリックした後に表示されるURL」を見て`link_pattern`を
組み立てると、的外れなパターンになることがある（過去に`ultragrace.com`で
発生。ブラウザ上は`ultra-blaze.com/top/girls/girldetail/?girl_id=...`や
`cityheaven.net/...`に転送されるが、ページのHTMLソースに実際に書かれている
`href`は全く別の`ultragrace.com/s/girl.php?id=...`だった）。

**教訓**: 必ず「ページのソースを表示」で確認した、転送前の生のURLを基準に
`link_pattern`を組み立てること。

### 6-2. 活動日(activity_date)のズレに注意

カレンダーサイトは、`checked_at`（チェックした日時）をそのままの日付では
なく、「`checked_at`のJST日付から1日引いたもの」を活動日として集計している
（`docs/index.html`の`activityDateFromChecked`関数）。0時のチェックが
「前日分の更新」を検知するという設計のため。

このルールにより、深夜（JST日付が変わった直後）に実行された手動チェックの
結果は、体感的には「今日やった」チェックでも、集計上は「前日」の活動日として
カウントされる。過去に、この認識のズレから「本来の数値と違う」という
問い合わせが何度か発生した。数値の食い違いを調査するときは、必ず
`checked_at`の実際のUTC時刻からJST日付・活動日を計算し直して確認すること。
体感的な「実行した日」を鵜呑みにしない。

### 6-3. `seen_links`をリセットする際の注意（新着の吸収）

`custom_pattern`の識別キーの仕様を変更した際など、既存の`seen_links`が
新しい形式と噛み合わなくなり、次回チェックで現在の一覧が丸ごと「新着」として
誤検知されることがある（いわゆる誤通知の洪水）。これを避けるため、該当する
お店の`seen_links`を`[]`（空）にリセットしてから新しいコードを反映する、
という対応を取ってきた。

ただし、これには副作用がある。リセットした瞬間にページに載っている項目は、
すべて「既知」として新しい基準に取り込まれ、二度と新着として通知されない。
つまり、**リセットの直前に実際に新しく入店していた人がいた場合、その人は
検知されないまま消えてしまう**。特に、最後にチェックした時刻からリセットが
反映されるまでに空白の時間があると（例: 深夜のチェックから、リセットが
実際に効いた午後まで新規チェックが走っていなかった場合）、その間に増えた
新着が黙って基準に飲み込まれてしまう。

**教訓**:
- `seen_links`のリセットが必要な場合は、対象を絞り込むときに`type=custom_pattern`の
  **全店舗**をSupabase上で確認すること（会話の流れで覚えている店舗だけを
  リセットすると、把握していなかった店舗が同じ問題を起こす。実際に
  ウルトラドリーム/ウルトラプラチナムでこれが発生した）。
- リセットは「なるべくチェックの直後」に行い、空白の時間を作らないようにする。
- リセット後は、その一次的な数値のズレが起きていないか、数日はカレンダーを
  注視する。

### 6-4. `custom_pattern`のクエリ文字列バグ（修正済み）

過去の`fetch_pattern_list_links`は、パターンを見る前に`href`の`?`以降を
無条件で切り捨てていた。このため、IDがクエリ文字列に含まれるサイト
（`girl.php?id=12345`のような形式）は、`link_pattern`をどう書いても
絶対に検知できないという設計上の不具合があった。

現在は、クエリ部分を切り捨てず、正規表現が一致した部分の文字列
（`re.Match.group(0)`）をそのまま識別キーとして使うように修正済み
（コミット`79e80ac`）。パスにIDがあるサイトにも、クエリ文字列にIDが
あるサイトにも、`link_pattern`の書き方だけで対応できるようになっている。

### 6-5. `403 Client Error: Forbidden`（サイト側のブロック）

登録直後に9店舗すべてが`403 Forbidden`で失敗したことがあった。これは
`link_pattern`の間違いではなく、**サイト側がアクセスそのものを拒否した**
ことが原因（プログラム的なアクセスだと判定するボット対策・不正アクセス
対策と見られる）。

対応として、`crawl.py`が送るリクエストヘッダーを、実際のブラウザに近い
内容（詳しいUser-Agent、Accept、Accept-Language）に変更した
（コミット`3b0bb5b`）。極端に短い`User-Agent: Mozilla/5.0`だけを送ると
「いかにもプログラムのアクセス」という目印になってしまうため。この対応で
上記の9店舗は解消した。

**ただし**、これで必ず解決するとは限らない。より高度なボット対策
（Cloudflareのチャレンジページ等）が入っているサイトでは、ヘッダーの
変更だけでは回避できない可能性がある。その場合は、そもそも今の
「シンプルなHTTPリクエストで巡回する」という方式では対応できない
可能性がある。

### 6-6. LINE通知に出ない4件目以降のリンクを見る方法

LINE通知は、見やすさのため各グループ先頭3件のリンクしか本文に載せない
（`notify.py`の`build_group_block`関数）。ただし`update_logs.new_items`には
1回のチェックにつき最大10件まで保存されているため、SQLで直接見ることができる。

```sql
select store_name, group_name, checked_at, new_count, new_items
from update_logs
where status = 'updated'
  and coalesce(group_name, store_name) = '対象のグループ名または店舗名'
  and checked_at >= '確認したい期間の開始(UTC)'
  and checked_at <  '確認したい期間の終了(UTC)'
order by checked_at;
```

1回のチェックで新着が10件を超えた場合、11件目以降は`new_items`に保存
されない（`new_count`自体は正確）。

### 6-7. 記録済みデータの手動修正について

`update_logs`は分析・実データとして扱われるため、明確な理由（プログラムの
不具合による誤カウント、実際は新着ではなかったものが混ざっていた、等）が
ない限り、勝手に数値を書き換えるべきではない。過去に「数値が想定と違う」
という相談を受けた際は、必ず以下の手順を踏んでいる。

1. 対象の期間・店舗・グループでSQLを実行し、実際に記録されている行を
   すべて洗い出す（重複行がないか、活動日の計算が原因で別の日に
   分類されていないか、を確認する）。
2. 原因を特定し、本当に修正が必要かを判断する（「本来の想定と違う」と
   感じても、実際には仕様通り正しく記録されているだけ、というケースが
   複数あった）。
3. 修正が必要な場合のみ、対象行の`id`を指定した`update`文で最小限の
   修正を行う（`new_count`と、対応する`new_items`の中身の両方を
   整合させる）。

「検証不要、この通りに直してほしい」と明確に指示された場合（例:
目視でイベント告知用のダミープロフィールだと確認済み、など）は、
上記の原因調査は省略してよい。

## 7. デプロイ・運用まわりのメモ

- GitHub ActionsのSecrets（`SUPABASE_URL` / `SUPABASE_SERVICE_KEY` /
  `LINE_CHANNEL_ACCESS_TOKEN`）はリポジトリの Settings → Secrets and
  variables → Actions に登録されている。コード中には一切ハードコードされて
  いない（`os.environ`経由でのみ参照）。
- リポジトリは公開(Public)設定になっている。GitHub Pagesを無料プランで
  使うための対応で、secretsは上記の通りコードに含まれていないため、
  公開しても機密情報が漏れることはない。
- `docs/index.html`（カレンダーサイト）はGitHub Pagesで公開されており、
  ブラウザから直接SupabaseのPublishable keyでデータを読み取る構成。
  そのため`rls_tighten_for_public_site.sql`で、Publishableキーには
  「読み取り専用」のRLSポリシーだけを設定してある（`crawl.py`/`notify.py`が
  使うSecret keyはRLSの制限を受けないため、巡回・通知には影響しない）。
  パスワード等のアクセス制限は設けていない（URLを知っていれば誰でも
  閲覧できる、非公開URL運用が前提）。
